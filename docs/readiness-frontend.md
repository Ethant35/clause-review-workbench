# Frontend readiness evidence

Author: Ethan

## Scope and result

The frontend remains a local, single-user React 18 and Vite application. It serves the existing local contract-review API. This pass adds first-run guidance, a replay path, pagination controls for bounded document and review-history responses, and protections against stale asynchronous document/review loads. It does not claim legal-analysis accuracy or hosted-service readiness.

First-run guidance supports both a real contract upload and a clearly labeled, synthetic text example. The example runs through the same local upload and configured playbook review endpoints; it does not contain a fabricated result. The guide can be skipped, persists that choice in a versioned local-storage key, and can be replayed from the footer. The browser stores only the dismissal marker; it does not store contract text, playbooks, or credentials. Completing a review dismisses first-run guidance. A replay remains available after success.

The document library requests 50 records at a time. Review history uses the API's summary mode and requests 50 rows at a time; selecting a history row fetches that review's complete evidence. Async document and review results are ignored after a newer selection takes ownership. Reviewer status and note edits send only the fields the reviewer changed.

The repeatable browser test is [frontend_readiness_e2e.py](../tests/frontend_readiness_e2e.py). Its latest run passed 14 checks; screenshots and the JSON report are in the ignored run directory `artifacts/frontend-readiness-b3upvs3t/`. The run used Chromium, a fresh SQLite data directory, the actual FastAPI server, text parsing, and real review API responses. It created 53 documents and 51 reviews to exercise both 50-row continuation controls. The API summary response included the documented metadata and revision flags and omitted issues, checks, playbook snapshots, and AI details. A test-only middleware held and then released one real document response to verify that a stale selection cannot win. axe-core was loaded locally from the pinned dev dependency and served from the same-origin built asset directory only for the test; the test removes that temporary copy before exiting.

Native browser zoom is separately exercised by [frontend_zoom_e2e.py](../tests/frontend_zoom_e2e.py). The latest run passed 9 checks in Chromium with an isolated temporary profile and a temporary Manifest V3 extension. The extension used Chrome's `tabs.setZoom()` and `tabs.getZoom()` API and confirmed factors 2.0 and 4.0; `window.devicePixelRatio` confirmed 2 and 4, producing 640 px and 320 px CSS viewport widths from a 1280 px browser viewport. At both zoom levels, the test used the actual local app: it uploaded and parsed the labeled synthetic contract, ran the configured playbook, inspected real findings, and navigated review tabs with the keyboard. The 1280×1000 screenshots capture the full physical browser viewport using Chromium's [Page.captureScreenshot](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-captureScreenshot) with `fromSurface=true` and `captureBeyondViewport=false`; I inspected the 200% and 400% images and confirmed they show the full viewport. The first capture attempt used Playwright `full_page=True`; at 400% it produced a 320-pixel-wide image showing only a clipped strip, so that image is not used as readability evidence. The zoomed page reflows without page-level horizontal overflow. At 400%, the tab strip uses its own horizontal scroll region; keyboard tab navigation also passed. No provider key was used, no external browser request occurred, and the backend socket audit was empty. The test removed its profile and extension after the run while retaining the report and screenshots in `artifacts/frontend-zoom-yucygj_n/`: [200% review](../artifacts/frontend-zoom-yucygj_n/review-200-percent.png), [400% review](../artifacts/frontend-zoom-yucygj_n/review-400-percent.png), and [JSON report](../artifacts/frontend-zoom-yucygj_n/report.json).

The zoom method follows the official [Chrome Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs#method-setZoom), which defines `setZoom()` and `getZoom()`, and Playwright's [Chrome extension guidance](https://playwright.dev/docs/chrome-extensions), which uses a persistent Chromium context for extensions. The test helper is temporary and has only the `tabs` permission; it is not installed in the user's browser.

This is not a full accessibility certification. The automated pass does not replace testing with VoiceOver, NVDA, or another assistive technology; no screen reader was tested. The true zoom run used Chromium on macOS; Safari, Firefox, Windows, Linux, and assistive-technology combinations remain unqualified. Loading and provider-error states are not exhaustively tested. The frontend does not fabricate or ship a sample legal result.

Pagination behavior must be qualified together with the backend summary endpoint and large-history cases. The frontend sends `limit`/`offset` for documents and `summary=true&limit=50&offset=…` for review history. The UI shows another-page action when a page contains 50 rows. Its correctness depends on the backend enforcing its documented maximum and returning summaries without issue bodies.
