## v1.2.0 status update

This section records the current release-level claims separately from the historical v1.1.0 audit below. The implementation reports `EXTRACTION_REVISION=4` and `REVIEW_REVISION=4`. The coordinator reports the current inventory as **87 pytest tests plus 2 subtests**. That count is supplied release evidence, not a test run performed while updating this document, and it is not a measure of legal accuracy. Earlier test totals below are preserved as the results of those earlier audit runs; they are not the current suite count.

The supported readiness claim remains limited to the single-user local macOS workflow exercised by the project. The available synthetic corpus, generated inputs, and local workflow tests do not establish broad contract-analysis accuracy, suitability for unsupervised legal decisions, or qualification of optional AI output. Optional AI remains an explicitly transmitted, citation-checked aid whose findings require human review. If an AI request may have reached the provider but its result is uncertain, the saved status is `OUTCOME_UNKNOWN` and the app does not retry automatically.

Current extraction boundaries include DOCX body paragraphs and nested table-cell paragraphs in XML order. Hidden text is rejected when the formatting is directly applied, inherited from referenced paragraph/run styles, or supplied by default paragraph/run styles. Headers, footers, and comments are not analyzed and produce warnings. Unsupported DOCX revisions, text boxes, notes, imports, macros, content controls, fields, and drawings remain rejected. PDF input is limited to text-based documents of at most 200 pages; PDFs with raster images or textless pages are rejected. Annotations/comments/form fields and possible side-by-side reading-order problems produce warnings. The side-by-side detector makes at most 100,000 block-pair comparisons per extraction and warns when that budget leaves pairs unchecked. These checks do not OCR, recover omitted content, or guarantee the PDF's visual reading order. Verify the source document.

The HTTP boundary also bounds request bodies and concurrent work, paginates document and review lists at 100 rows, and provides a review-history summary projection. Reviewer decisions support partial PATCH updates. An AI attempt is persisted as `IN_PROGRESS` before transmission and becomes `OUTCOME_UNKNOWN` after ambiguous interruption; recovery does not retry it. Local diagnostics are bounded and private and omit document/request payloads. The local recovery guide is [docs/recovery.md](recovery.md).

## Confirmed findings and changes

The liability-cap interaction recognizer accepted a narrow group of phrases, such as “the liability cap does not apply to indemnification obligations” and “indemnification obligations are uncapped.” It missed other explicit relationships in separate paragraphs. I reproduced three false-compliant inputs: indemnification obligations “are excluded from the foregoing cap,” the “foregoing limitations do not apply” to them, and they “are not subject to the liability cap.” Those forms left the fee-based cap check `COMPLIANT` and produced no cap interaction. The recognizer now links these named categories to the cap and sets the result to `NEEDS_REVIEW`. It retains the exact cap and exception blocks as evidence. The negative control “the foregoing cap does not exclude indemnification obligations” remains `COMPLIANT`; the configured fraud/willful-misconduct-only exception remains `COMPLIANT`; adding indemnification to that list produces `NEEDS_REVIEW`.

This is a scope warning, not a determination that an excluded claim is unlimited. A separate category limit may still apply. The explanation tells the reviewer to check the category limit, scope, conditions, and precedence. The implementation does not choose a party perspective or declare a market position.

DOCX extraction returned text hidden by a referenced character style as ordinary paragraph text. The source used an inherited `w:rStyle` with `w:vanish`; `python-docx` included that text in `p.text`, while the existing hidden-text check inspected only the document body XML. A second reproduction hid all text through `docDefaults`. The extractor now rejects referenced hidden paragraph/run style chains and hidden default run formatting. Visible DOCX body paragraphs and nested table cells retain XML document order and exact source offsets in generated fixtures.

PDF extraction did not disclose text annotations, comments, or form fields that were omitted from `get_text("blocks")`. It also had no visible warning when a page contained side-by-side text blocks whose extracted block order may differ from the visual reading order. The parser now emits warnings for annotations/comments/form fields and side-by-side blocks. It caps the side-by-side comparison at 100,000 pairs and warns when that check reaches its limit. These warnings ask the reviewer to verify the original. They do not make the PDF representation complete.

The same source-fidelity review found that DOCX comment text lives outside the body paragraphs and was silently omitted. The parser now warns when it finds the comments part or comment-range/reference markers. This is a warning because the operative body remains extractable, but the comment may contain review context or a proposed exception that is absent from the extracted contract text.

The final review found two more edge cases. Hidden formatting on default paragraph or character styles applies even when paragraphs/runs omit explicit style references; those documents are now rejected too. Also, the PDF side-by-side detector now checks the pair budget inside the inner comparison loop, so it performs at most 100,000 comparisons per extraction. For cap interactions, category labels shown to reviewers are readable names such as “indemnification” and “confidentiality”; regex patterns remain internal to detection.

Because interpretation changed, `REVIEW_REVISION` is now 4. Because the parser now rejects hidden-style documents that older revisions accepted, `EXTRACTION_REVISION` is now 4; old extracted documents must be re-uploaded before a new review. `review_view` now requires both the review and extraction revisions to match before labeling a review current. This change fixed a reproduced status bug where a matching review revision could conceal a stale extraction revision. Existing decisions and notes remain stored and are rendered as historical. The v1.0.0 upgrade run passed its first four preservation and historical-warning checks; its browser rerun step stopped because the new onboarding dialog exposed a second “Run review” button to the existing strict Playwright locator. The remaining upgrade checks were not established by that run.

## Verification

- `PYTHONPATH=backend .venv/bin/python -m pytest tests/test_analysis_readiness.py -q`: **24 passed**. Hypothesis ran 260 generated examples across three properties. PyMuPDF emitted five SWIG deprecation warnings.
- `PYTHONPATH=backend .venv/bin/python -m pytest -q`: **38 passed** across the Python test suite. PyMuPDF emitted five SWIG deprecation warnings; Starlette reported that its `httpx`-based `TestClient` is deprecated.
- `.venv/bin/python tests/adversarial_e2e.py --output artifacts/readiness-adversarial-expanded.json`: **83/83** real HTTP, parser, and API checks. This retains all 81 fixed prior cases and adds two DOCX checks for inherited hidden styles and hidden document defaults.
- `.venv/bin/python tests/interactions_e2e.py --no-browser --output artifacts/readiness-interactions-final.json`: **97/97** real HTTP/API, parser, persistence, source-evidence, and export checks.
- The interaction browser flow was attempted twice during concurrent UI changes. One run reached related-source navigation then timed out waiting for the save-note status; the later run timed out looking for a document row beyond the initial page. The headless interaction suite passes; browser interaction is not claimed here.

Supported extraction remains deliberately narrow. Plain text uses UTF-8. DOCX body paragraphs and nested table-cell paragraphs are read in XML order; headers and footers are omitted with a warning, as are comments. Tracked changes, footnotes/endnotes, fields, drawings, embedded objects, content controls, macros, hidden text (including inherited default paragraph/character styles), and unsupported imports are rejected. PDF extraction is for text-based files of at most 200 pages; raster images and empty-text pages are rejected. PDF annotations/comments/form fields are not extracted and now produce a warning. Side-by-side text blocks produce a reading-order warning. The layout detector performs at most 100,000 block-pair comparisons and warns if more remain unchecked. The parser does not OCR or guarantee visual reading order, and source verification against the original remains necessary.

These checks do not qualify extraction against all Word/PDF producers, OCR, DOCX headers and footers or comment semantics, embedded objects, fields, or complex PDF reading order. The property-based binary test is bounded to 2 KiB inputs and is not coverage-guided native fuzzing; PyMuPDF itself includes native MuPDF code that this Python test cannot instrument. No independent lawyer panel or held-out contract set was available, so legal interpretation remains experimental and must be checked against the original agreement by a qualified reviewer.
